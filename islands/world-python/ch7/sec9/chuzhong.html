9.1.2.1 一切从"逐个走过"开始 It all starts with iteration

9.2.2 累加器三部曲（The Accumulator Pattern）

9.2.2.1 归零 → 逐个累加 → 返回 Zero, add each, return

求和函数有一个雷打不动的三段式套路。它和第一单元的"计数器三部曲"是同一个家族——只不过计数器每次固定 +1，而累加器每次加上的是元素的实际值。

🧮 累加器三部曲
①归零：循环前把累加器设为 0，如 totalValue = 0
②逐个累加：循环体内 totalValue += coins[i].value
③返回结果：循环结束后 return totalValue，把总和交出去
三者缺一不可——少了①总和会出错，少了②不会累加，少了③外面拿不到结果。

9.2.3 对象数组求和（Summing Object Properties）

9.2.3.1 加的不是硬币本身，而是它的 value 属性 Add the property, not the object

这里有一个关键细节：许愿井里的数组元素不是纯数字，而是硬币对象。正如关卡所说："我们有一个对象（硬币）数组，所以我们要把每个硬币的 value 属性加起来。"因此累加时写的是 coins[coinIndex].value 而不是 coins[coinIndex]——要用点号取出那枚硬币的价值属性再相加。下面是许愿井里 sumCoinValues() 的写法：

def sumCoinValues(coins):
    coinIndex = 0
    totalValue = 0              # ① 累加器归零
    while coinIndex < len(coins):
        totalValue += coins[coinIndex].value   # ② 加上这枚硬币的价值
        coinIndex += 1
    return totalValue          # ③ 返回总价值
value 与 len 的区别：len(coins) 数的是硬币的数量（有几枚），而 coin.value 是每枚硬币的面值（值多少）。许愿井要求"刚好 104 个硬币"，其实比较的是所有硬币的价值总和是否等于 104——两枚 1 分银币和一枚 2 分金币在数量上是 3 枚，但价值总和也可能相同，理解这一点才能读懂这一关。

9.4 多分支条件判断

Handling Multiple Cases

9.4.1 三种情况分别处理（Three Branches）

9.4.1.1 不够、太多、刚好 Too little, too much, just right

拿到金币总值后，许愿井要求根据结果落在哪个区间做出不同反应：不够就喊 "Non satis"、太多就喊 "Nimis"、刚好 104 就开始收集。这需要并列的多个 if 判断把数轴切成三段，每段对应一个动作。

拉丁语彩蛋：许愿井里用的是拉丁语——"Non satis" 意思是"不够"，"Nimis" 意思是"太多"。喊出正确的话，井才会给出反馈。三个 if 分别对应三条互不重叠的数轴区间，无论金币总值是多少，永远只会命中其中一条。

9.4.2 == 与 != 的用法（Comparison Operators）

9.4.2.1 判断相等用 ==，判断不相等用 != Equality and inequality

许愿井还用到了两个重要的比较运算符。判断两个值是否相等用 ==（两个等号，别和赋值的单个 = 混淆）；判断是否不相等用 !=。关卡里先用 if goldAmount != 0 确认"井里确实有硬币"（不为 0 才继续），再用 if goldAmount == requiredGold 确认"总值刚好达标"。

goldAmount = sumCoinValues(items)
if goldAmount != 0:              # 井里有硬币才判断
    if goldAmount < requiredGold:
        hero.say("Non satis")   # 不够
    if goldAmount > requiredGold:
        hero.say("Nimis")       # 太多
    if goldAmount == requiredGold:
        collectAllCoins()          # 刚好，开始收集
最经典的坑：千万别把 == 写成 =。= 是"赋值"（把右边存进左边），== 才是"比较是否相等"。在 if 条件里写错成 = 会直接报错。记忆口诀："一个等号是给予，两个等号是询问。"

关卡 · 许愿井

🪙 许愿井 —— 求和判断与综合应用

图2：许愿井——先求出硬币总值，判断是否刚好 104，再决定收集还是等待

策略：先算总值，再按区间反应

许愿井要求你收集刚好 104 的金币总值，不多不少。整关的策略是一条清晰的链条：先用 sumCoinValues() 求出井里所有硬币的价值总和，再拿这个总和和目标值 104 比较，落在哪个区间就做哪个动作——不够喊 "Non satis"、太多喊 "Nimis"、刚好就调用 collectAllCoins() 把硬币全收进来。整个判断包在 while True 里，因为井里的硬币会变化，需要持续监测。

思路拆解

算法思路是四步走：第一步，每轮用 hero.findItems() 感知井里当前的硬币数组；第二步，把数组交给求和函数得到 goldAmount；第三步，先用 if goldAmount != 0 排除"井里暂时没硬币"的空档；第四步，用三个并列的 if 按 < / > / == 分别处理不够、太多、刚好三种情况。关键在于——收集动作只在"刚好等于 104"时才触发。

# 关键片段：求和 + 三分支判断
goldAmount = sumCoinValues(items)
if goldAmount == requiredGold:   # 只有刚好才收集
    collectAllCoins()

算法看点：函数在这里"各司其职"

这一关最漂亮的地方，是它把大问题拆成了几个各司其职的小函数：sumCoinValues(coins) 只负责"算总和"，collectAllCoins() 只负责"把硬币收干净"，主循环只负责"判断该走哪条分支"。这种职责分离的设计，正是本单元想让你体会的综合能力——每个函数都简单到一眼看懂，组合起来却能完成复杂任务。

collectAllCoins 的小技巧：收集函数内部用的是"边找边收"的经典写法：item = hero.findNearest(hero.findItems()) 找到最近的硬币，走过去捡起，然后再找一次更新 item；只要还找得到（while item）就继续，找不到了自然停下。这正是第一单元"用变量做循环条件、循环内更新变量"的应用。
读懂再动手：关卡特意提示"看一下 sumCoinValues() 的代码，看看它怎么做到的"。这是复习单元的用意——先读懂别人写好的函数，理解累加器模式，再把它用起来。学会读代码，和学会写代码同样重要。
易错提醒：不要把 collectAllCoins() 放到三个判断之外无条件调用，否则不管够不够都会去收集，就失去了"精确凑数"的意义。收集必须严格绑定在 == requiredGold 这一条分支里。

9.6 常见错误

Common Mistakes

9.6.1 新手最容易踩的坑（Pitfalls for Beginners）

9.6.1.1 求和与综合应用的典型问题 Typical issues in this review unit

图3：累加器忘记归零、混淆 = 与 ==、漏加 .value，是本单元最常见的失误
易错点清单：
  • 累加器忘记归零——没写 totalValue = 0 就直接累加，总和从一开始就是错的。
  • 漏加 .value——写成 totalValue += coins[i] 而不是 coins[i].value，试图把"硬币对象"加进数字，会出错。
  • 混淆 = 与 ==——条件里判断相等要用 ==，单个 = 是赋值。
  • return 位置错误——把 return totalValue 写进 while 循环里，会导致才加一枚就提前返回，总和不完整。
  • 忘记索引自增——漏掉 coinIndex += 1，卡在第一枚硬币上死循环。
  • 收集动作放错位置——把 collectAllCoins() 放在判断之外，导致不管够不够都去收集。
  • 没排除空数组——漏掉 if goldAmount != 0，井里暂时没硬币时会误判为"不够"而反复喊话。
