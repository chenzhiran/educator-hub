12.1 事件处理入门

Getting Started with Event Handling

12.1.1 顺序执行 vs 并行（Sequential vs Parallel）

12.1.1.1 代码本来是"排队"执行的 Code normally runs in line

"快速赛跑"关卡一开场就点明了一个基础事实："通常而言，代码会按顺序执行：下一条命令运行之前，必须要等前一条先执行完。" 这就是顺序执行（Sequential Execution）——一行做完才轮到下一行，像排队一样。

可是在赛跑关卡里，如果英雄先跑、宠物再跑，宠物永远追不上。关卡给出了解法："如果将宠物的代码放入事件处理器函数，那就会和英雄的代码并行运行！" 这里出现了本单元的核心思想——并行（Parallel）：让宠物和英雄的代码同时跑起来，而不是一个等另一个。

12.1.2 什么是事件处理器（What Is an Event Handler）

12.1.2.1 "听到信号才触发"的特殊函数 A function triggered by a signal

事件处理器（Event Handler）本质上是一个函数，但它很特别：它不由你主动调用，而是当某个"事件"发生时，由系统自动触发执行。你只需提前写好这个函数、并把它"登记"到某个事件上，之后每当那个事件发生，函数就会自动运行。

比如"快速赛跑"里的 petMove 函数，登记给了 "spawn"（出生/登场）事件——宠物一登场，这个函数就自动执行，宠物就跑了起来，完全不用等英雄那行代码。

🔔 事件处理器的"三步曲"
第一步：定义一个函数（写好"事件发生时该做什么"）
第二步：用 on() 把它绑定到某个事件名上
第三步：等待触发——事件一发生，函数自动执行，与主代码并行
你负责"写好+挂上"，系统负责"在对的时机喊它起来"。

12.1.3 on() 绑定事件（Binding with on()）

12.1.3.1 pet.on(事件名, 函数) pet.on(eventName, handler)

绑定事件用的是 on() 方法。它接收两个参数：第一个是事件名字符串（如 "spawn"、"hear"），第二个是要绑定的函数名（注意：只写函数名，不加括号）。

def petMove(event):
    pet.moveXY(50, 21)

pet.on("spawn", petMove)   # 绑定：宠物一登场就跑
hero.moveXY(50, 12)       # 英雄同时也跑
最易错的一点：绑定时写 pet.on("spawn", petMove) 而不是 pet.on("spawn", petMove())。加了括号意味着"立刻调用这个函数、把它的返回值传进去"，那就完全错了——我们要传的是函数本身，让系统日后去调用它。

12.2 宠物与类型查找

Pets & Finding by Type

12.2.1 findNearestByType（按类型查找）

12.2.1.1 用类型字符串精准定位 Locate by a type string

"沙漠蘑菇"关卡介绍了宠物的独特能力："findNearestByType 接受一个字符串参数，表示你要找的物品/单位的类型。" 有了它，宠物不需要"特殊眼镜"就能按类型挑出你想要的东西——比如只找药水、不碰有毒的蘑菇。

potion = pet.findNearestByType("potion")   # 只找药水
skeleton = pet.findNearestByType("skeleton") # 也能找敌人
不止找物品："蘑菇之声"关卡强调，findNearestByType 找的不仅仅是物品——它同样能找骷髅、弓箭手、巫师等单位。凡是有"类型"的对象，都能用它精准定位。

12.2.2 fetch 取物（Fetching Items）

12.2.2.1 让宠物"叼"东西回来 Let the pet retrieve items

找到了还得取回。pet.fetch(item) 让宠物去拾取并运送某件物品给英雄。"蘑菇之声"关卡特别说明：宠物 fetch 只是搬运，不会消耗或使用物品——它把药水叼过来，药水还是完整的药水。这在"钥匙陷阱"这类关卡尤其重要，因为英雄本人去碰钥匙会触发陷阱，而让宠物 fetch 就安全了。

potion = pet.findNearestByType("potion")
pet.fetch(potion)   # 宠物把药水叼回来给英雄

12.3 事件参数 event

The event Parameter

"命令链"关卡揭示了事件处理器更深的一层："事件处理器函数会获得触发事件（event）的信息。" 那个几乎每个处理器都写着的 event 参数，其实装着关于"这次事件到底怎么回事"的宝贵数据。对 "hear"（听到声音）事件来说，最有用的是两个属性：event.speaker 和 event.message。

12.3.1 event.speaker（谁说的话）

12.3.1.1 认出声音来自哪个单位 Identify who is speaking

event.speaker 是发出声音的那个单位。"命令链"关卡用它让宠物只回应英雄："你就可以让宠物只回应英雄说的话。" 判断方法是把 speaker 和某个已知单位作比较：

def onHear(event):
    if event.speaker == hero:   # 只有英雄说话才回应
        pet.say("WOOF")

pet.on("hear", onHear)
过滤发言人：很多关卡（如"宠物探索者""危险钥匙""奥林匹克比赛"）都要求只听特定角色的话，忽略别人。核心手法就是先用 findNearestByType 或 findNearestFriend 拿到"该听的那个单位"，再用 if event.speaker == 那个单位 把其他人的声音全部滤掉。

12.3.2 event.message（说了什么）

12.3.2.1 读取声音的内容 Read the spoken content

event.message 是被说出来的那句话，是个字符串。"宠物翻译家"关卡用它解密雇佣兵的命令，"宠物副官"用它区分"Fire"和"Heal"两种指令。判断方法就是把 message 和目标字符串比对：

def onHear(event):
    if event.message == "Fire":
        pet.moveXY(64, 16)
    elif event.message == "Heal":
        pet.moveXY(64, 52)

12.3.3 二者联合判断（Combining speaker & message）

12.3.3.1 既看是谁说、又看说了啥 Check both who and what

最严谨的判断会同时用上 speaker 和 message——先确认"是不是该听的人"，再确认"他说了什么"。"奥林匹克比赛"就是典范：宠物必须等裁判（而不是粉丝）说出"Start"才起跑，用 and 把两个条件连起来：

referee = pet.findNearestByType("wizard")
if event.speaker == referee and event.message == "Start":
    pet.moveXY(53, 27)   # 只有裁判喊 Start 才起跑

12.4.1 快速赛跑（Sprint）

12.4.1.1 策略：把宠物代码搬进事件处理器 Strategy: move pet code into a handler

图2：快速赛跑——宠物代码放进 spawn 处理器，与英雄并行冲线

这是事件处理的首秀。算法思路极简却关键：定义 petMove(event) 让宠物跑向终点，然后用 pet.on("spawn", petMove) 绑定到"出生"事件。要点在于理解"为什么这样能赢"——如果宠物代码写在主线程里，它得等英雄那行跑完；而搬进事件处理器后，宠物在"登场"瞬间就并行开跑，两者同时冲刺，宠物才追得上。

12.4.2 沙漠蘑菇 & 蘑菇之声（Mushroom Levels）

12.4.2.1 策略：宠物送药、英雄看血收集 Strategy: pet fetches potions, hero watches health

图3：沙漠蘑菇——宠物在处理器里不停送药，英雄在主线程按血量安全收集

这两关首次让"事件处理器 + findNearestByType + fetch"三件套协同工作。算法思路是分工并行：在 onSpawn 处理器里让宠物用 findNearestByType("potion") 不断找药水并 fetch 送来；英雄则在主 while 循环里收集蘑菇，但加一道血量守卫——只有当 hero.health > hero.maxHealth / 3 时才去碰有毒的蘑菇。宠物负责"续命"，英雄负责"采集"，两条线各跑各的。

"蘑菇之声"进阶为按顺序取多样物品：处理器里先 fetch 药水、再 fetch 金钥匙，英雄则先打骷髅、骷髅倒下后再去开箱。关键是理解宠物的取物动作与英雄的战斗是并行推进的。

12.4.3 钥匙陷阱（The Key to Success）

12.4.3.1 策略：钥匙交给宠物，英雄绝不亲取 Strategy: let the pet handle the trapped keys

图4：钥匙陷阱——宠物依次 fetch 铜、银、金三钥匙，英雄专心御敌

这一关的核心策略是"危险的活交给宠物"：英雄本人去拿钥匙会中陷阱，所以在 onSpawn 里让宠物连续 fetch 三把钥匙（铜、银、金），英雄则在主循环里对付食人魔、并在血量低时让宠物去找药水。思路要点是分清"谁该做什么"——宠物承担搬运，英雄承担战斗，两者互不阻塞。拼写三种钥匙类型时务必准确。

12.4.4 命令链（Chain of Command）

12.4.4.1 策略：用 event.speaker 只认英雄 Strategy: respond only to the hero

这一关引入 event.speaker。算法思路是：在 onHear 里判断 if event.speaker == hero，只有英雄说话时宠物才回应"WOOF"去唤醒巫师；英雄则在主循环里发现敌人后 say("Ogres!") 报警，再按路线移动。关键在于理解"发言人过滤"——场上可能有很多声音，必须靠 speaker 锁定唯一该响应的对象。

12.4.5 宠物工程师（Pet the Engineer）

12.4.5.1 策略：按发言人分派宠物去不同按钮 Strategy: route the pet by who called

图5：宠物工程师——听弓箭手呼救去左按钮，听士兵呼救去右按钮

这一关把 event.speaker 用出了"分支路由"的味道。算法思路是：先用 findNearestByType 分别拿到 archer 和 soldier 两个单位，再在处理器里用 if/elif 判断 event.speaker 到底是谁——是弓箭手就去左按钮 (32,30)，是士兵就去右按钮 (48,30)。核心思想是"根据谁在呼救，决定宠物去哪"，speaker 成了选择动作的依据。

12.4.6 宠物翻译家 & 宠物副官（Message Levels）

12.4.6.1 策略：用 event.message 决定动作 Strategy: act on the message content

图6：宠物翻译家——把听到的方位词倒过来念，为炮兵翻译命令

这两关的主角是 event.message。"宠物翻译家"的思路是把听到的消息映射成另一句话：听到 "North" 就说 "Htron"、"South" 就说 "Htuos"——用一串 if 做"消息→翻译"的对照表。"宠物副官"则是把消息映射成动作：听到 "Fire" 移到底部、"Heal" 移到顶部。妙处在于消息由英雄在主循环里根据战况动态喊出（血量低喊 "Heal"、遇强敌喊 "Fire"），宠物听令而动——这就是主线程与事件处理器"喊话—响应"的协作模式。

12.4.7 炼金术（Alchemy）

12.4.7.1 策略：听令则取药，否则回待命点 Strategy: fetch on command, else return

这一关把 message 判断和 fetch、待命结合起来。算法思路是：在 onHear 里，若 event.message == "Fetch" 就让宠物 fetch 药水送给正在战斗的英雄；否则（else）让宠物回到红色待命标记。这体现了一个实用模式——事件处理器不仅规定"该做什么"，也规定"没轮到时待在哪"，让宠物始终处于随时待命的状态。

12.4.8 概念挑战合集：宠物探索者 · 危险钥匙 · 奥林匹克比赛

12.4.8.1 策略：speaker + message 双重把关 Strategy: filter by speaker and message together

图7：奥林匹克比赛——只听裁判喊"Start"才起跑，避免抢跑犯规

这三个挑战关卡是本单元的综合考场，共同套路是"先认人、再听话"。"宠物探索者"要只听探索者、不听农民，再按他报的数字 1/2/3 去对应按钮；"危险钥匙"要只听圣骑士，按她说的 Gold/Silver/Bronze 取对应钥匙；"奥林匹克比赛"要只听裁判、且只在他喊 "Start" 时起跑。

通用算法骨架：这类关卡都可归纳为同一套结构——① 在处理器外或内先 findNearestByType/findNearestFriend 锁定"该听的单位"；② 用 if event.speaker == 该单位 过滤掉无关声音；③ 在其内部再用 if event.message == ... 的分支决定具体动作。先过滤发言人、再解析消息内容，是响应式事件编程的经典范式。

12.5 常见错误

Common Mistakes

12.5.1 新手最容易踩的坑（Pitfalls for Beginners）

12.5.1.1 事件处理的典型问题 Typical issues with event handling

图8：绑定加括号、类型拼错、忘记 event 参数，是本单元最常见的失误
易错点清单：
  • 绑定时给函数名加了括号——写成 pet.on("spawn", petMove())，应为不带括号的 petMove，否则传的是返回值而非函数本身。
  • 处理器函数漏写 event 参数——像 def onHear(): 会导致无法接收事件数据，应写 def onHear(event):。
  • 类型字符串拼写/连字符错误——"gold-key" 写成 "goldkey" 或 "gold_key"，宠物就找不到。
  • 混淆 speaker 与 message——speaker 是"单位"要和单位比较，message 是"字符串"要和字符串比较，两者不能对调。
  • 忘记过滤发言人——不判断 event.speaker 就响应，结果宠物听了农民或粉丝的话，导致抢跑或走错。
  • 比较 message 时忘了引号或写错大小写——"Start" 写成 Start（变量）或 "start"（小写）都匹配不上。
  • 误以为事件处理器会阻塞主线程——它其实是并行运行的，主 while 循环不会等它，需理解两条线各自独立。
