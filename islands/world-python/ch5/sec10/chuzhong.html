10.1 生命值属性

Health Attributes

10.1.1 health 与 maxHealth（Current and Max Health）

10.1.1.1 当前血量和血量上限 Current health vs the maximum

前几单元你学会了读取对象的 pos、type 等属性。本单元再添几个至关重要的属性，首先是生命值。每个战斗单位都有两个血量属性：health 是当前血量（随受伤减少、随治疗回升），maxHealth 是血量上限（满血时的数值，通常固定不变）。

current = hero.health      # 英雄现在还剩多少血
maximum = hero.maxHealth   # 英雄满血是多少
为什么要两个属性:只看 health 无法判断"伤得重不重"——满血 100 时剩 40 算重伤,满血 1000 时剩 40 已濒死。必须把 health 和 maxHealth 结合起来看比例,才能得出"还剩几成血"这个真正有用的信息。

10.1.2 用比例设阈值（Thresholds with Proportions）

10.1.2.1 用除法算出"一半""三分之一" Use division for halves and thirds

"医疗护理"关卡教了核心技巧：用除法运算符 / 把 maxHealth 除以一个数，得到一个"阈值"，再拿 health 和它比较。比如 maxHealth / 2 就是"半血线"，maxHealth / 3 就是"三分之一血线"。当 health 低于这条线，就说明该撤退治疗了：

healingThreshold = hero.maxHealth / 2   # 半血线
if hero.health < healingThreshold:
    hero.moveXY(65, 46)
    hero.say("Heal please!")
阈值的妙处:把"maxHealth / 2"存进一个名字清晰的变量(如 healingThreshold),既让代码读起来像自然语言("如果血量低于治疗阈值"),又方便调整——想改成三分之一血才治疗,只需把 / 2 改成 / 3,一处修改处处生效。

10.1.3 读取他人的血量（Reading Others' Health）

10.1.3.1 敌人也有 health 和 maxHealth Enemies have health too

和 pos 一样，生命值属性也是"万物皆有"的。enemy.health 是敌人当前血量、enemy.maxHealth 是敌人血量上限。"王之谷"就利用这一点——只在骷髅血量大于其最大血量三分之一时才攻击（血太低就跑）：

if enemy.health > enemy.maxHealth / 3:
    hero.attack(enemy)
else:
    hero.moveXY(35, 16)   # 血低了就撤

10.2 时间属性

The Time Attribute

10.2.1 hero.time（Reading the Clock）

10.2.1.1 读取游戏已经过去的秒数 How many seconds have elapsed

"守时"关卡引入了 hero.time 属性。它表示自按下运行按钮以来已经过去了多少秒，是一个随游戏进行不断增大的数字。有了它，你就能让英雄"看表行事"——在不同的时间段做不同的事：

if hero.time < 10:       # 前 10 秒
    ...

10.2.2 elif 分阶段（Phases with elif）

10.2.2.1 用 else-if 串起多个时间段 Chain time phases with else-if

要按时间划分多个阶段，就需要 elif（else-if）。"守时"关卡解释："if 语句可以和 else-if 配合使用，只有第一个 if 为 false，且第二个 if 为 true 时后一个 if 才会执行。" 这样几个 elif 串起来，就构成了一条"要么这样、要么那样"的互斥判断链：

if hero.time < 10:          # 阶段一: 前10秒,攻击
    ...
elif hero.time < 35:        # 阶段二: 10~35秒,收集硬币
    ...
else:                        # 阶段三: 35秒后,再次攻击
    ...
elif 的顺序很关键:因为 elif 是"前面都不成立才轮到我",所以判断要从小到大排。time < 35 这一条只有在 time < 10 不成立(即已过10秒)时才会被检查,所以它实际覆盖的是"10 到 35 秒"这一段。理解这种"层层过滤"的逻辑,是用好 elif 链的核心。

10.3 价值与金币

Value and Gold

10.3.1 item.value（An Item's Worth）

10.3.1.1 每个物品都有价值 Every item has a value

物品也有属性。item.value 表示一个物品值多少金币。第七单元"春雷"里我们就用 value 区分过银币（值 2）和蓝宝石（值 10）；本单元则用它来累计收集到的财富。coin.value 读出这枚硬币的价值：

worth = coin.value   # 这枚硬币值多少钱

10.3.2 hero.gold（Your Purse）

10.3.2.1 英雄身上的金币总数 The gold the hero currently holds

"诱饵演习"引入了 hero.gold——英雄目前实际持有的金币数。它和自己用变量累加的计数器不同：hero.gold 是游戏自动维护的、你真正能花的钱。建造单位（如 "decoy" 诱饵）需要消耗金币，所以要先检查 hero.gold 够不够：

if hero.gold >= 25:          # 钱够 25 才建造
    hero.buildXY("decoy", hero.pos.x, hero.pos.y)

10.3.3 累加计数器（Accumulator Counter）

10.3.3.1 用变量自己记账 Keep your own running total

"囤积黄金"让你用一个变量当"账本"，把每枚硬币的价值累加起来。这就是编程中经典的累加器（accumulator）模式：先在循环外把计数器初始化为 0，每收集一枚硬币就用 += 把它的 value 加进去：

totalGold = 0                    # 循环外: 账本清零
while True:
    coin = hero.findNearestItem()
    if coin:
        hero.moveXY(coin.pos.x, coin.pos.y)
        totalGold += coin.value  # 每收一枚就记一笔账
初始化必须在循环外:计数器 totalGold = 0 一定要写在 while 之前! 如果错放到循环里面,每转一圈它都被重置为 0,永远也累加不起来。"先在外面清零,再在里面累加"是累加器模式雷打不动的规矩。

10.4 break 与自定义函数

"break" and Custom Functions

10.4.1 break 跳出循环（Breaking a Loop）

10.4.1.1 提前终止 while 循环 Exit the loop early

"囤积黄金"引入了 break 语句。关卡解释："当你 break 一个循环时，循环会马上终止运行，且程序将会执行循环之后的代码。" 平时 while True 会永远转下去，但配合 break，我们就能在满足某个条件（比如凑够 25 金）时主动跳出，去执行循环后面的收尾动作：

while True:
    # ... 收集硬币、累加 totalGold ...
    if totalGold >= 25:
        break                    # 凑够了,跳出循环

# 循环结束后才会执行到这里
hero.moveXY(58, 33)
hero.say(totalGold)
🚪 break 像"紧急出口"

while True 本是一间没有门的房间,程序会一直在里面打转。break 就是墙上凿出的一扇紧急出口——一旦条件满足,程序立刻从这扇门走出去,继续执行循环下方的代码。没有 break,那些收尾代码永远等不到执行的机会。

10.4.2 定义自己的函数（Defining Functions）

10.4.2.1 用 def 打包一段动作 Package actions with def

"Kithgard附魔师"让你第一次定义自己的函数。关卡说，函数的第一个好处就是把一大堆代码缩减为一行，还让代码更易理解。定义函数用 def 关键字，包含函数名和函数体两部分：

def moveRight():              # 函数名: moveRight
    x = hero.pos.x + 12    # ↓ 函数体: 调用时执行的代码
    y = hero.pos.y
    hero.moveXY(x, y)

moveRight()                   # 定义好后,一行就能调用
"定义"和"调用"是两回事:def moveRight(): 只是定义——告诉程序"moveRight 这个词代表这段代码",本身不会执行任何动作;真正让英雄动起来的是后面那句 moveRight() ——这才是调用。定义写一次,调用可以写很多次,这正是函数省事的地方。

10.5.1 Kithgard附魔师（Kithgard Enchanter）

10.5.1.1 策略：定义三个移动函数再调用 Strategy: define three move functions, then call them

图1：Kithgard附魔师——自定义 moveRight/moveUp/moveDown 三个函数,组合出通关路线

这是自定义函数的入门关。任务是定义 moveRight、moveUp、moveDown 三个函数，每个让英雄相对移动 12 米，然后按正确顺序调用它们走出地牢。算法思路是：每个函数内部都用第九单元学的"读当前坐标 → 加减 12 → moveXY"来实现相应方向的移动；定义好后，在下方按路线依次 moveRight()、moveDown()、moveUp()…… 调用。核心是理解定义与调用分离，以及函数如何把一段坐标计算浓缩成一个好记的名字。

10.5.2 生命值关卡：扫雷 / 医疗护理（Health Levels）

10.5.2.1 策略：血量低于阈值就撤退治疗 Strategy: retreat to heal below the threshold

图2：医疗护理/扫雷——用 maxHealth/2 设半血线,受重伤就撤退求医,否则继续行动

这两关都靠"生命值阈值"决策。"扫雷"要用身体引爆硬币下的地雷带农民过峡谷，血量太低就向左撤 10 米请医生治疗；"医疗护理"则是边战斗边在受伤时撤到治疗师处。算法思路一致：先算 healingThreshold = hero.maxHealth / 2，用 if hero.health < healingThreshold 判断是否重伤——是就撤退并 say 求治疗，elif/else 才继续正常行动（收集硬币或攻击敌人）。核心是把"生存"放在最高优先级——先保命，再干活。

关键洞察:注意判断顺序——"是否需要治疗"必须放在最前面用 if 判断,收集/攻击放在 elif/else。这样一旦重伤,程序会优先执行撤退,而不会先去贪一枚硬币或补一刀。用条件的先后顺序表达优先级,是策略类关卡的通用智慧。

10.5.3 Killdeer操作 / 王之谷（Boolean-Return Levels）

10.5.3.1 策略：用返回布尔值的函数封装"该不该跑" Strategy: wrap "should I run" in a boolean function

图3：Killdeer操作——写 shouldRun() 返回布尔值,血量过低时诱敌撤退到陷阱

"Killdeer 操作"把生命值判断封装进一个返回布尔值的函数，复习了第四单元的返回值知识。算法思路是：定义 shouldRun() 函数，内部判断 hero.health < hero.maxHealth / 2，血量过半就 return True、否则 return False；主循环里用 if shouldRun(): 决定跑向陷阱还是继续战斗。"王之谷"（概念挑战）则直接用 enemy.health > enemy.maxHealth / 3 判断——敌人血量高才打、血低就撤。核心是体会：把复杂的血量判断封装成一个名字清晰的函数，主逻辑就变得像读句子一样简单。

10.5.4 守时（On the Clock）

10.5.4.1 策略：用 hero.time 和 elif 链分阶段行动 Strategy: phase actions by time with an elif chain

图4：守时——按 hero.time 分三阶段:先助战、再攒钱、后再战

这一关是时间属性的核心演练。任务是按游戏时间分阶段行动。算法思路是用一条 if/elif/else 链：if hero.time < 10——前 10 秒协助战斗；elif hero.time < 35——10 到 35 秒收集硬币攒资源；else——35 秒后再次投入战斗。关键在于理解 elif 链的"层层过滤"——第二个条件只有在第一个不成立时才被检查，所以 time < 35 实际管的是"10~35 秒"这一段。这一关教你让程序按时间节奏自动切换策略。

进阶提示:关卡还提醒——最后战斗吃紧时,可以在血量低时让英雄撤退(结合本单元的生命值知识);若敌人类型是 "palisade"(栅栏)则不必攻击。这说明真实关卡往往要把多个单元的知识叠加运用:时间分阶段 + 生命值保命 + 类型筛选,一起构成完整策略。

10.5.5 沙漠十字（Desert Combat / Cross）

10.5.5.1 策略：用命名布尔变量组合出对角方向 Strategy: name boolean vars to compose diagonals

图5：沙漠十字——把上下左右判断存成 isAbove/isLeft 等布尔变量,再用 and 组合出四个对角

这一关把第九单元的坐标比较升级成更清晰的写法。食人魔从对角线四个角进攻，你要判断方位并在对应角建火焰陷阱。算法思路的巧妙之处在于：先把四个方向判断分别存进命名布尔变量——isLeft = hero.pos.x > enemy.pos.x、isAbove = hero.pos.y < enemy.pos.y 等；再用 and 组合出对角方向，如 if isLeft and isAbove: 在左上角建陷阱。这样代码读起来就是"如果在左边且在上面"，一目了然。

命名布尔变量的价值:关卡特意对比了两种写法——直接写 hero.pos.x > enemy.pos.x and hero.pos.y < enemy.pos.y 又长又难懂;而先存成 isLeft、isAbove,再写 isLeft and isAbove,则既好写又好读。给中间结果起个好名字,是让复杂逻辑清晰化的高级技巧。

10.5.6 金币收集关卡：囤积黄金 / 诱饵演习 / 贪婪保护 / 千岩谷

10.5.6.1 策略：累加计数 + 达标 break Strategy: accumulate, then break when the goal is met

图6：囤积黄金/诱饵演习——收集到目标金额或数量后 break 跳出循环,再执行收尾

这几关都围绕"金币 + 计数 + break"展开。"囤积黄金"用 totalGold += coin.value 累加价值，达到 25 就 break，出循环后向 Naria 报数。"诱饵演习"则用 hero.gold 判断——够 25 金就建一个诱饵、给 decoysBuilt 加 1，建满 4 个就 break。"贪婪保护"（概念挑战）收集到 99 金后 break 逃向安全区。"千岩谷"（组合挑战）则综合坐标移动、比较运算和血量比例，跟着发光石穿越山谷。

算法思路的共性是"循环外初始化计数器 → 循环内累加并判断 → 达标 break → 循环后收尾"这套完整框架。它把"重复做某事直到攒够"这一常见需求，用可靠的结构表达了出来。

gold 与自建计数器的区别:"囤积黄金"用自己的变量 totalGold 记账,而"诱饵演习"用系统的 hero.gold。区别在于:hero.gold 是可花费的真实金钱(建造会扣减),而 totalGold 只是你自己的统计数字(不会因花钱而减少)。根据你是要"统计收集量"还是"检查购买力",选用对应的那一个。

10.6 常见错误

Common Mistakes

10.6.1 新手最容易踩的坑（Pitfalls for Beginners）

10.6.1.1 属性与循环控制的典型问题 Typical issues with attributes and loop control

图7：计数器放错位置、混淆 health/maxHealth、忘调用函数,是本单元最常见的失误
易错点清单：
  • 计数器初始化放进了循环——totalGold = 0 若写在 while 里，每轮清零永远攒不够，必须放在循环外。
  • 混淆 health 与 maxHealth——判断重伤要用 health < maxHealth / 2，别把两者写反或只用其中一个。
  • 比例阈值漏括号或除错数——想要"三分之一血"是 maxHealth / 3，别错写成别的数或忘了除。
  • 只定义函数却忘了调用——写了 def moveRight(): 却没写 moveRight()，英雄不会动。
  • 忘记写 break 或 break 条件错——没有 break 的 while True 永不结束，循环后的收尾代码永远执行不到。
  • elif 顺序排反——时间/血量阈值要从小到大或按优先级排，顺序错会让某些分支永远进不去。
  • 把 hero.gold 当自建计数器改——hero.gold 由系统维护，不能像普通变量那样随意赋值累加。
  • 累加时用了 = 而非 +=——写成 totalGold = coin.value 会每次覆盖而非累加，得用 +=。
