5.1 认识不等于运算符

Meet the "Not Equal" Operator

5.1.1 从 == 到 !=（From == to !=）

5.1.1.1 你已经会 ==，现在学它的反面 You know ==, now meet its opposite

上一单元你熟练使用了 ==——它的意思是"等于"，用来判断两个值是不是相同。本单元登场的新运算符长得跟它很像，叫 不等于运算符（Not Equal Operator），写作 !=。"穿越"关卡一句话点题："你已经知道 == 意思是等于。!= 看着挺像，不过它是不等于。"

!= 判断两个值是不是不同。如果两个值不一样，它返回 True；如果两个值相同，它返回 False。可以说，!= 就是 == 的"镜像双胞胎"——它俩的结果永远相反。

图1：!= 是 == 的反面——== 问"一样吗?"，!= 问"不一样吗?"
表达式含义当两值相同当两值不同
a == ba 等于 b 吗?TrueFalse
a != ba 不等于 b 吗?FalseTrue

5.1.2 != 的语法解剖（Anatomy of !=）

5.1.2.1 一个感叹号加一个等号 An exclamation mark plus an equals sign

"穿越"关卡介绍语法：要比较两个值是否不相等，把 != 写在两个值中间即可。在英语里，感叹号 ! 常用来表示"非"（not），后面跟上 =（等于），合起来就是"不等于"。

别写错:不等于是 !=，不是 =!，也不是 <>（那是别的语言的写法）。感叹号一定在前，等号在后，中间不能有空格。另外要牢记，判断相等是两个等号 ==，一个等号 = 是"赋值"，含义完全不同。

5.1.3 != 返回布尔值（!= Returns a Boolean）

5.1.3.1 结果不是 True 就是 False The result is either True or False

和 == 一样，!= 是一个比较运算符，它的运算结果是一个布尔值（Boolean）——不是 True 就是 False。正因为如此，!= 特别适合放进 if 的条件里，用来给程序做"分流"判断：

# item.type 是 "gem" 吗? 若不是,条件成立
if item.type != "gem":
    hero.moveXY(item.pos.x, item.pos.y)   # 不是宝石才去捡

当 item.type 的值确实不是 "gem"（比如是 "coin" 或 "food"），item.type != "gem" 就返回 True，if 里的动作就会执行；如果它正好是 "gem"，表达式返回 False，动作被跳过。

5.2 != 的核心用法

Core Uses of !=

5.2.1 "排除法"思维（Thinking by Exclusion）

5.2.1.1 与其列举全部"能做"，不如指出唯一"不能做" Name the one exception, not every allowed case

这是本单元最重要的思想。"奇境"关卡说得非常透彻："当有很多正条件、只有一个负条件时，你可以使用它。这里无需在执行动作之前枚举所有条件，只需使用 != 一次就能描述相反的所有情况。"

设想战场上有硬币、食物、药水、材料等很多种物品，你想全部收集，唯独不要宝石。如果用 ==，你得写一长串："如果是硬币，或者是食物，或者是药水……" 又累又容易漏。但用 !=，一句话就够了——"只要不是宝石，就收集"：

# 笨办法: 枚举所有"能捡"的类型(又长又易漏)
if item.type == "coin" or item.type == "food" or item.type == "potion":
    ...

# 聪明办法: 只指出唯一"不能捡"的类型
if item.type != "gem":
    ...
更深的价值:"奇境"关卡还点出一个妙处——"在不完全知道所有'正'条件时，只要知道不能做什么，你也可以使用它。" 也就是说，就算你不知道战场上到底会出现多少种物品，只要清楚"宝石不能碰"，用 != 就能安全地处理所有其它情况。这让代码更健壮、更能适应变化。

5.2.2 按 type 属性筛选（Filtering by type）

5.2.2.1 用 != 配合 .type 挑出目标 Pair != with the .type attribute

本单元几乎每一关都在做同一件事：读取物品或敌人的 .type 属性，用 != 和某个类型字符串比较，从而决定"要不要动手"。常见的类型有：宝石 "gem"、毒药 "poison"、树精 "burl"、小兵 "peon" 等。

🎯 筛选的通用套路

先找到对象(findNearestItem 或 findNearestEnemy)，确认它存在，再用 对象.type != "某类型" 判断它不是那种要回避的东西，成立就行动。一句话概括:"找到它 → 确认存在 → 确认不是禁区类型 → 行动。"

enemy = hero.findNearestEnemy()
if enemy:                          # ① 确认敌人存在
    if enemy.type != "peon":    # ② 不是"peon"才打
        hero.attack(enemy)          # ③ 行动

5.2.3 != 与 not 的区别（!= vs not）

5.2.3.1 一个比较两值，一个反转布尔 One compares values, one flips a boolean

"有用的对手"关卡还引入了逻辑非（not）运算符。它和 != 都跟"否定"有关，容易混淆，务必分清：!= 是比较运算符，比较两个值是否不同，结果是布尔值；not 是逻辑运算符，它把一个已有的布尔值反转——True 变 False，False 变 True。

# != 比较两个值是否不同
if enemy.type != "peon":   # type 不是 peon → True

# not 反转一个布尔值
if not enemy:                # 没有敌人时 → True
    hero.say("周围很安全!")
经验法则:要判断"两个值是否不同",用 != 最清楚(例如 type != "gem");要把一个"是/否"的判断整体翻个面,用 not 最清楚(例如 not found)。它俩甚至可以互相改写——a != b 等价于 not (a == b),但直接写 != 通常更易读。

5.3 实战关卡精讲

Level Strategy & Analysis

这一节聚焦每一关的策略、思路与算法设计，看懂"该用 != 排除什么、条件怎么组织",你就能自己写出完整解法。

5.3.1 穿越（Friend and Foe / Passage）

5.3.1.1 策略：非宝石跟宠物,是宝石去捡 Strategy: not a gem → follow pet, else → collect

图2：穿越——闯入友善兽人村庄,只能拿他们递来的宝石,别碰其它食物

这是 != 的入门关。剧情很有意思:你来到一个友善兽人村庄,规矩是——拿走他们的食物、或不收下他们给的宝石,都会激怒他们。所以这一关的"正确目标"恰恰是宝石,其它物品都要回避。

算法思路是配合 if/else 两条分支:找到物品后,先判断 item.type != "gem"——如果不是宝石,说明这是不该碰的东西,那就 moveXY 跟着宠物走开;else 分支(即它是宝石)才移动到物品坐标去收集。核心是体会 != 如何把"是/不是"两种情况干净地分开。

关键洞察:这一关的 != 和 else 是一对搭档——if item.type != "gem" 处理"不是宝石"的情况,else 自动兜住"剩下的情况"也就是"是宝石"。你只需要写清一个条件,另一半交给 else,逻辑既完整又不重复。

5.3.2 有用的对手（Helpful Minions）

5.3.2.1 策略：非小兵才打,非毒药才捡 Strategy: attack non-peons, collect non-poison

图3：有用的对手——战场混着硬币与毒药,用 != 筛掉毒药、放过差役

这一关同时处理敌人和物品两条线,并首次引入 not 运算符的概念。战场上食人魔在进攻、差役想偷你的硬币,而地上的硬币里混着致命的毒药。

算法思路分两段,都靠 != 排除:第一段找最近敌人,只在 enemy.type != "peon"(不是小兵/差役)时 attack——放过无害的差役,专打真正的威胁;第二段找最近物品,只在 item.type != "poison"(不是毒药)时 moveXY 去捡——避开毒药,收集硬币。两段逻辑并列写在同一个 while True 循环里,英雄边打边捡。

一循环两任务:这一关展示了如何在一个主循环里并列处理多件事——先处理敌人,再处理物品。两段代码各自独立,各用一次 != 做筛选。这种"分块并列"的结构在后面的关卡里会反复出现。

5.3.3 奇境（Wonderglade）

5.3.3.1 策略：收集除宝石外的一切 Strategy: collect everything except gems

图4：奇境——树精守着宝石,用一次 != 就能"收集除宝石外的所有物品"

这一关是理解"排除法"最好的例子。奇境能提供任何物品,你要来收集食材和硬币,但树精喜欢闪亮的宝石、不许你拿。物品种类繁多,若逐一枚举可收集的类型会非常繁琐。

算法思路极简:主循环里找到最近物品,确认存在后,只判断一个条件 item.type != "gem"——只要不是宝石,就 moveXY 过去收集。一次 != 顶替了一长串 or,这正是本单元反复强调的核心智慧:与其列举所有能做的,不如指出唯一不能做的。

5.3.4 被诅咒的梦境（Cursed Wonderglade）

5.3.4.1 策略：两个 != 分别管物品和敌人 Strategy: two != blocks for items and enemies

图5：被诅咒的梦境——枯树与飞雪中,既要收集(非宝石)又要战斗(非树精)

这一关把前面几关的技巧综合起来。梦境被食人魔诅咒,变得阴森。规则有两条:树精还在收集宝石,所以别碰宝石("gem")、也别攻击树精("burl");其余物品都收集、其余敌人都击败。

算法思路是在 while True 里写两个并列的判断块:第一块处理物品,if item 且 item.type != "gem" 时收集;第二块处理敌人,if enemy 且 enemy.type != "burl" 时攻击。两块结构对称、各用一次 !=——这是"有用的对手"那种"一循环两任务"模式的自然延伸。

嵌套 if 的作用:每一块都是两层 if 嵌套——外层 if item: 先确认对象存在(防止对着"空"取 .type 而报错),内层 if ... != ... 再筛类型。先确认存在、再判断类型,这个顺序不能颠倒,是稳健代码的基本功。

5.3.5 狂野联盟（概念挑战 · Wild Alliance）

5.3.5.1 策略：只攻击非树精的敌人 Strategy: only attack non-burl enemies

这是本单元的概念挑战,用来检验你是否真正掌握了 !=。任务纯粹而明确:只攻击 type 不是 "burl" 的敌人,也就是放过树精、打击其它所有敌人。

算法思路是最经典的"筛选套路"三步走:主循环里 findNearestEnemy 找到最近敌人 → if enemy 确认它存在 → if enemy.type != "burl" 确认它不是树精 → attack 攻击。因为是概念挑战,系统不再给注释提示,需要你独立回忆并组织这套结构。

# 只攻击类型不是 "burl" 的敌人
while True:
    enemy = hero.findNearestEnemy()
    if enemy:
        if enemy.type != "burl":   # 不是树精才出手
            hero.attack(enemy)
概念挑战的意义:概念挑战刻意去掉了脚手架式的注释提示,考验你能否脱离提示独立成篇。如果这一关你能顺手写出上面的结构,说明 !=、.type 属性和"确认存在再判断"的套路已经真正内化成你的本能了。

5.4 常见错误

Common Mistakes

5.4.1 新手最容易踩的坑（Pitfalls for Beginners）

5.4.1.1 不等于运算符环节的典型问题 Typical issues with the != operator

图6：符号写反、漏引号、把 != 当 not、忘记确认存在,是本单元最常见的失误
易错点清单：
  • 符号写反或写错——把 != 写成 =!、=/= 或漏掉感叹号,程序会报语法错误。
  • 类型字符串漏引号——写成 item.type != gem(没引号)会被当成变量而报错,必须写 "gem"。
  • 类型名拼错或大小写不符——"Gem"、"burls" 都不等于 "gem"、"burl",筛选就会失效。
  • 把 != 和 not 搞混——!= 比较两个值,not 反转一个布尔值,用途不同别乱套。
  • 忘记先确认对象存在——没写 if enemy: 就直接读 enemy.type,当周围没敌人时会因对着"空"取属性而出错。
  • 把判断相等的 == 误写成赋值的 =——一个等号是"赋值",两个才是"比较",条件里必须用比较。
  • 误用 == 逐一枚举——想排除一种类型时,还傻傻地用一长串 or 列举其余类型,既啰嗦又易漏,应该直接用一次 !=。
