3.1 布尔值与比较

Booleans and Comparison

3.1.1 布尔值 True / False（The Boolean）

3.1.1.1 非真即假的一种值 A value that's either true or false

本单元让英雄学会"做判断"。一切判断的基础，是一种特殊的值——布尔值（Boolean）。"叫阵"关卡定义道："布尔值是 True（真）和 False（假）二者取其一的值。"

不同于数字可以有无数个、字符串可以千变万化，布尔值只有两种可能：要么 True，要么 False。它就像一个开关，非开即关，没有第三种状态。判断"对不对""成不成立"的结果，正是用布尔值来表示的。

图1：布尔值就像一个开关——只有 True 和 False 两种状态

3.1.2 比较产生布尔值（Comparison Yields a Boolean）

3.1.2.1 比一比，得出真或假 Compare two values, get true or false

布尔值从哪来？最常见的来源就是比较。关卡说："使用比较运算符对比两个值。比较的结果要么是 True（成立），要么是 False（不成立）。"

比如 4 == 4 这个比较，问的是"4 和 4 相等吗？"答案显然是"相等"，所以它的值就是 True。而 4 == 5 问"4 和 5 相等吗？"答案是"不相等"，它的值就是 False。一个比较表达式，最终会"算"出一个布尔值。

3.1.3 if 语句的判断（The if Statement）

3.1.3.1 条件为真才执行 Run the block only when true

布尔值最重要的用武之地是 if 语句。关卡解释："if 语句是说：'如果（if）这个为 True，那么就做那个。' if 内的代码块只会在条件成立（值为 True）时才会运行。"

所以 if 的工作流程是：先把条件算成一个布尔值，如果是 True 就执行下面缩进的代码块，如果是 False 就跳过。"叫阵"关卡的玩法正是修改条件让它变成 True，从而触发英雄说出激怒食人魔的话。

3.2 相等运算符 ==

The Equality Operator ==

3.2.1 == 检查是否相等（Checking Equality）

3.2.1.1 两个等号，问"相等吗？" Two equals signs ask "are they equal?"

本单元的核心运算符是相等运算符（==）。关卡介绍："我们首先要接触的比较运算符是等于运算符。在 Python 和 JavaScript 中，该运算符被记作 ==。" 它检查两侧的值是否相等，相等得 True，不等得 False：

4 == 4      # 值为 True
4 == 5      # 值为 False

3.2.2 == 与 = 的区别（== vs =）

3.2.2.1 一个比较，一个赋值 One compares, one assigns

这是初学者最容易混淆的一点，关卡郑重警告："注意这里是两个等号连在一起，是 ==，而不是 =。一个等号是赋值运算符，用于为变量赋值！新编程者容易混淆这两个运算符！"

运算符名称作用示例
=赋值运算符把右边的值存进左边的变量x = 5（让 x 等于 5）
==相等运算符比较两边是否相等，得布尔值x == 5（x 是 5 吗？）
关键区分：记住一句口诀——"一个等号是'变成'，两个等号是'是不是'"。在 if 条件里要判断相等，必须用 ==。写成一个 = 是赋值，会导致语法错误或逻辑错误。

3.2.3 与运算结合使用（Combining with Arithmetic）

3.2.3.1 先算数，再比较 Calculate first, then compare

"叫阵"关卡演示了 == 可以和上单元的数学运算符结合：先把两边的算式各自算出结果，再比较是否相等。例如：

2 + 2 == 4    # 左边算出 4，4 == 4 → True
2 + 2 == 5    # 左边算出 4，4 == 5 → False

运算优先于比较：+ 先做完，得到的结果再交给 == 判断。这种"先计算后比较"的组合，让条件可以表达更复杂的判断。

3.3 type 类型属性

The "type" Property

3.3.1 type 是字符串属性（type Is a String Property）

3.3.1.1 告诉你"这是什么" Tells you what something is

上单元你学会了读 pos 属性。本单元的明星属性是 type。"濒危树瘤之战"关卡介绍："每种敌人都有一个属性，名为 type（类型），表示为字符串（引号内的数据内容，例如 'thrower'）。"

"嘲弄"关卡进一步强调它的普遍性："所有的单位和物品都有 type 属性。这个属性是非常重要的，因为它让你能够对不同类型的敌人/朋友/物品定义不同的战术。" 食人魔有矮人（"munchkin"）、斗士（"brawler"）、投掷手（"thrower"）等，还有树瘤（"burl"）等——读 type 就能分辨它们。

3.3.2 type 后不加括号（No Parentheses After type）

3.3.2.1 属性不是方法 A property is not a method

关卡两度强调一个容易犯的错："注意 type 是一种属性，而不是 moveXY(20, 20) 那样的方法。type 后不可以使用 ()。"

💡 属性 vs 方法：读数据 vs 做动作

方法是让对象"做一件事"，要带括号，如 hero.moveXY(20, 20)、hero.attack(enemy)。属性是对象"自带的一份数据"，直接读取、不带括号，如 enemy.type、enemy.pos。写成 enemy.type() 是错的——type 不是动作，不能被"调用"。

3.3.3 按类型分流战术（Branch by Type）

3.3.3.1 用 type == 决定怎么打 Use type == to choose tactics

把 type 属性和 == 运算符结合，就能针对不同类型的单位采取不同行动。这是本单元最强大的组合：

if enemy.type == "munchkin":   # 读 type 并比较
    hero.attack(enemy)             # 矮人 → 攻击
if enemy.type == "ogre":
    hero.moveXY(41, 47)         # 食人魔 → 逃跑

这样英雄就能"看人下菜"：矮人就打、投掷手也打、树瘤忽略、强敌逃跑。读类型 → 比较 → 分流行动，是处理多种对象的通用算法。

3.4.1 叫阵（Taunt）

3.4.1.1 策略：把条件改成 True 来触发嘲讽 Strategy: make conditions true to taunt

图2：叫阵——修改 if 条件使其为 True,让英雄喊话把食人魔引入雷区

这是布尔值与 if 的入门关。任务是让英雄说出激怒食人魔的话,把它们诱入雷区。算法思路是修改 if 后面的比较条件,使其值为 True——比如把条件改成 3 + 3 == 6(成立)或 20 == 20(成立),条件为真,下面的 hero.say 就会执行。这一关的精髓在于亲手体验"条件为 True 才触发动作"这一核心机制。

理解要点:只有当 == 两侧真正相等时,比较才得 True,if 块才运行。亲手把 2 + 2 == 5(False)改成相等的式子,就能直观看到条件真假如何决定代码是否执行。

3.4.2 濒危树瘤之战（Endangered Burl）

3.4.2.1 策略：按 type 分四类应对 Strategy: handle four types differently

图3：濒危树瘤之战——按 type 决定攻击、忽略还是逃跑

这一关首次把 type 和 == 结合实战。地图上混杂着多种单位,要求区别对待:攻击 "thrower" 和 "munchkin",忽略 "burl"(濒危树瘤,不能伤害),遇到 "ogre" 强敌则逃往村口。算法思路是用多个 if 分别检查 enemy.type,每种类型对应一种行动。读类型、比较、分流——三步构成清晰的应对逻辑。

关键洞察:同样是循环找最近敌人,但行动不再是"见敌就打",而是先看它是什么类型,再决定怎么办。type 属性让英雄从"莽夫"升级为"会判断的战术家"。注意 type 后绝不能加括号。

3.4.3 嘲弄（Munchkin Swarm）

3.4.3.1 策略：把分流逻辑封进函数 Strategy: wrap branching logic in a function

图4：嘲弄——攻击矮人、呼叫斗士、忽略树精,逻辑封装成函数

这一关把"按类型分流"和前面学过的函数结合起来。任务是攻击矮人("munchkin")、呼叫斗士("brawler",因为斗士要用陷阱对付)、忽略树精。算法思路是定义一个 dealEnemy(enemy) 函数,把"检查 type 并采取对应行动"的逻辑封装其中,主循环里找到敌人就调用它。这样代码既清晰又易复用。

设计巧思:把"类型判断 + 行动"打包成带参数的函数,是非常好的组织方式。主循环只管"找敌人、交给函数处理",具体怎么分类应对则藏在函数里。这正是第八单元"多参数函数"与本单元"类型判断"的融会贯通。

3.4.4 错误的类型（概念挑战 · Wrong Type）

3.4.4.1 策略：用类型过滤,只打特定敌人 Strategy: filter by type, attack only one kind

这是概念挑战,要击败至少 10 个 "munchkin",但绝不能误伤其他单位——树精、骷髅不主动惹你,而今天农民穿了蓝衣会被 findNearestEnemy 当成敌人找到,却万万不能打。算法思路是:找到最近敌人后,用 if enemy.type == "munchkin" 作为过滤器,只有类型确实是矮人才攻击,其余一律放过。

enemy = hero.findNearestEnemy()
if enemy:
    if enemy.type == "munchkin":  # 类型过滤器
        hero.attack(enemy)            # 只打矮人
算法本质:这里 type == "munchkin" 充当了一道"身份核验"——找到的不一定是该打的。先核验类型再动手,既完成了任务,又避免误伤无辜。这是"类型判断"作为安全过滤器的典型应用。

3.5 常见错误

Common Mistakes

3.5.1 新手最容易踩的坑（Pitfalls for Beginners）

3.5.1.1 判断与类型环节的典型问题 Typical issues with comparison and type

图5：== 写成 =、type 加括号、类型拼写错,是本单元最常见的失误
易错点清单：
  • 把 == 写成 =——条件判断必须用两个等号，一个等号是赋值。
  • 给 type 加括号——enemy.type() 是错的，type 是属性不是方法，应写 enemy.type。
  • 类型字符串拼写或大小写错误——"munchkin" 必须用引号且拼写准确，"Munchkin" 不相等。
  • 忘记给类型加引号——enemy.type == munchkin 会把 munchkin 当变量，应加引号。
  • 没先判断敌人是否存在——直接读 enemy.type 而 enemy 为空时会出错，要先 if enemy:。
  • 误伤不该打的单位——没用类型过滤就攻击，可能打到农民或濒危树瘤。
