6.1 布尔值回顾

Booleans Recap

6.1.1 什么是布尔值（What Is a Boolean）

6.1.1.1 只有两种取值的数据类型 A data type with only two values

要学好逻辑运算符 or，得先牢牢握住它的原料——布尔值。"Burl和布尔"关卡讲得很清楚："和字符串或数字一样，布尔也是一种数据类型。" 只不过它特别简单——布尔值（Boolean）要么是 True（真），要么是 False（假），没有第三种可能。

关卡还特别提醒了 Python 的书写规则：在 Python 中，布尔值是 True 或 False，首字母必须大写。这和 JavaScript 里小写的 true/false 不一样。此外，字符串 "true"（带引号的文本）和布尔值 True 是两种完全不同的东西，不能混为一谈。

6.1.2 比较运算返回布尔（Comparisons Return Booleans）

6.1.2.1 == != < > 都会算出 True 或 False == != < > all evaluate to a boolean

布尔值最常见的来源，就是提问。"Burl和布尔"关卡点明：编写代码时，判断某个问题"是真还是假"非常有用。最典型的问题就是关于相等的——"A 是否等于 B?"，用等于运算符 == 写作 A == B，它的答案就是一个布尔值。

表达式提问结果
2 == 32 等于 3 吗?False
3 == 33 等于 3 吗?True
1 + 2 == 31+2 等于 3 吗?True
"Three" == 3文本"Three"等于数字3吗?False
2 + 2 < 52+2 小于 5 吗?True
血泪教训:"Burl和布尔"反复强调——赋值用一个等号 =(如 enemy = hero.findNearestEnemy())，判断相等用两个等号 ==。误把 == 写成 =，会让程序调试"充满血与泪"。这是初学者最经典、也最难自查的错误之一。

6.1.3 if 靠布尔值分流（if Runs on Booleans）

6.1.3.1 条件为 True 才执行代码块 The block runs only when the condition is True

"宝石或者死亡"关卡把 if 的本质说透了："if 控制的代码块只会在条件成立（值为 True）时才会运行。" 换句话说，if 就像一道闸门——只有当括号里的表达式算出 True，门才打开、里面的代码才执行；算出 False，门关着，代码被跳过。理解了这一点，你就掌握了控制程序走向的钥匙。

6.2 逻辑运算符 or

The Logical "or" Operator

6.2.1 or 的含义（What "or" Means）

6.2.1.1 两个布尔值"相加"得一个布尔值 Combine two booleans into one

"盐碱地"关卡正式引入了逻辑或（or）。它给了一个绝妙的类比："将 or 放置在两个布尔值之间会返回一个布尔值，这就像使用 + 将两个数字加起来得到一个数字。" 数字用 + 相加得数字，布尔值用 or "相加"得布尔值。

or 的规则可以用一句大白话记住："只要有一个为真，结果就为真。" 关卡原话是——"or 前后的两个布尔值，如果至少有一个为 true，则 or 返回 true；如果两个都为 false，则 or 返回 false。" 这非常符合我们日常说的"或"：只要满足其中之一即可。

🍬 生活中的 or

妈妈说:"你考到 90 分,或者帮我做一周家务,就给你买糖。" 只要你做到任意一件——哪怕两件都做到——都能拿到糖;只有两件都没做到,才拿不到。这就是 or 的逻辑:一真则真,全假才假。

6.2.2 or 的真值表（Truth Table of "or"）

6.2.2.1 四种组合,只有一种为 False Four cases, only one is False

把 or 左右两边所有可能的取值列出来，就得到一张真值表。它是 or 行为的完整"说明书"，值得记牢：

左边 A右边 BA or B
TrueTrueTrue
TrueFalseTrue
FalseTrueTrue
FalseFalseFalse

一眼就能看出规律：四种组合里，只有"两边都为 False"时结果才是 False，其余三种都是 True。 所以判断 or 的结果有个快捷法——先找有没有 True，只要找到一个，就可以直接下结论"整体为 True"了。

6.3 用好 or

Making the Most of "or"

6.3.1 合并多个 if（Merging Multiple ifs）

6.3.1.1 一个 or 顶替好几段重复代码 One "or" replaces repeated blocks

"流星雨"关卡道出了 or 最实用的价值："逻辑或运算符可以让代码易读，且能帮助避免重复。" 设想你既想捡硬币、又想捡宝石。如果不用 or，你得写两段几乎一模一样的 if：

# 啰嗦: 两段几乎重复的 if,动作还一样
if item.type == "gem":
    hero.moveXY(item.pos.x, item.pos.y)
if item.type == "coin":
    hero.moveXY(item.pos.x, item.pos.y)

而用 or，一段就够了——把两个条件用 or 连起来，共用同一段动作：

# 简洁: 一个 if 搞定两种情况
if item.type == "gem" or item.type == "coin":
    hero.moveXY(item.pos.x, item.pos.y)
为什么"不重复"很重要:"流星雨"关卡指出——避免重复代码是好习惯,因为它让代码更易读,而且以后想改逻辑时只用改一个地方。如果动作代码抄了两遍,哪天要修改就得两处都改,漏改一处就会出 bug。这是编程里著名的 DRY 原则(Don't Repeat Yourself,别重复自己)。

6.3.2 混搭比较运算（Mixing in Comparisons）

6.3.2.1 or 两边可以是不同种类的判断 The two sides can be different kinds of checks

or 的威力不止于连接两个 ==。"盐碱地"关卡强调，<、>、<=、>=、== 这些运算都会返回布尔值，把它们结合起来会更有用。"流星雨"就是绝佳例子：一边判断"是不是宝石"（==），另一边判断"距离够不够近"（<），两个毫不相干的问题用 or 连成一句话：

distance = hero.distanceTo(item)
# 是宝石(总要捡) 或者 距离小于20米(近的硬币才捡)
if item.type == "gem" or distance < 20:
    hero.moveXY(item.pos.x, item.pos.y)

这句话的意思是："只要它是宝石，或者它离我不到 20 米，我就去拿。" 宝石永不消失所以总要捡，硬币会很快消失所以只捡近的——两种截然不同的收集规则，被 or 优雅地合并成了一个判断。

6.3.3 or 与 != 的取舍（"or" vs "!="）

6.3.3.1 白名单用 or，黑名单用 != "or" for allow-lists, "!=" for deny-lists

上一单元的 != 和本单元的 or 都能做筛选，但思路正好相反，值得对比着理解。or 是"白名单"思维——明确列出你想要的几种，比如"是宝石或是硬币就捡"；!= 是"黑名单"思维——指出你唯一不要的那种，比如"只要不是宝石就捡"。

场景推荐写法理由
只要 2-3 种明确的目标a == X or a == Y目标少而明确,正面列举更清楚
除某一种外都要a != X反面只有一个,排除法最省事
目标很多、种类不定a != X无需枚举全部,只需守住禁区
选择的智慧:没有哪个运算符"更好",关键看情况。"想要的东西少" → 用 or 一一列出;"不想要的东西少" → 用 != 一次排除。学会根据问题的形状挑选合适的工具,是从"会写代码"迈向"写好代码"的关键一步。

6.4.1 宝石或者死亡（Gems or Death）

6.4.1.1 策略：调试条件,让该跑的跑、该停的停 Strategy: debug conditions to control flow

图2：宝石或者死亡——不写新代码,只调试 if 条件的真假,避开雷区、走向宝石

这是理解 if 与布尔值的热身关，特别之处在于——你几乎不用写新代码，只需要"调试"。关卡给了一串 if，每个后面注释着"把它设为 True"或"把它设为 False"。你要修改条件表达式（比如改数字、改运算符），让通往宝石的动作条件为真、通往雷区的动作条件为假。

算法思路的核心是逆向思考:先决定"我想不想让这个动作发生"，再倒推"条件该是真还是假"。想让 moveXY 到宝石就把它的条件改成成立(如把 2+2==4 保持为真);不想踩雷就把雷区那句改成不成立(如把 1+1+1==3 改成 ==4 让它为假)。这一关还顺带复习了 ==、!=、< 和 not 各自如何影响真假。

关键洞察:这一关教会你一个宝贵的调试视角——程序的走向完全由条件的真假决定。看到一个不想要的动作,别急着删代码,先问"是哪个条件让它为真的?" 修条件往往比改逻辑更精准。这种"从结果倒推条件"的思维贯穿整个编程生涯。

6.4.2 Burl和布尔（Burl and Boolean）

6.4.2.1 策略：亲手算出每个问题的真假 Strategy: evaluate each question by hand

图3：Burl和布尔——树精出题考你,用 hero.say 回答每个 == 问题的真假

这一关是布尔值的"口试"。树精 Burl 连出几道判断题，每道题上方的注释给出一个表达式（如 2 == 3、"Three" == "Three"、1 + 2 == 3），你要用 hero.say(...) 说出它的正确答案——True 或 False。

算法思路就是逐题在脑中当一次"人肉解释器"：先算出 == 两边各是什么，再判断它们是否真的相等。要点在于识别陷阱：数字 3 和文本 "Three" 永远不相等（类型都不同），而 "Three" == "Three" 两个一模一样的字符串则相等。做完这一关，你对"表达式如何求值成布尔"就有了扎实的直觉。

6.4.3 盐碱地（Salted Earth）

6.4.3.1 策略：用 or 列出该打的敌人和该捡的物品 Strategy: list valid enemies and items with "or"

图4：盐碱地——保卫定居点,用 or 圈定打击目标与收集目标,避开毒药与树精

这是 or 的正式登场关。任务是保卫定居点：收集硬币、击败食人魔，但要避开地上的毒药和无辜的树精。场上目标种类多，正好用 or 把"想要的几种"一一圈出来。

算法思路是两段并列逻辑,各用一次 or:处理敌人时,if enemy.type == "munchkin" or enemy.type == "thrower" 才 attack——只打这两种食人魔;处理物品时,if item.type == "coin" or item.type == "gem" 才 moveXY 去捡——只收硬币和宝石,毒药因不在名单里被自动跳过。这正是 or "白名单"思维的典型应用。

白名单的安全感:用 or 列白名单有个好处——凡是没列进来的,一律不碰。毒药、树精你甚至不用专门去"排除",只要没把它们写进 or 名单,英雄就不会理它们。当"危险的东西"种类不确定时,只列"安全的东西"反而更省心、更保险。

6.4.4 流星雨（Meteor Shower）

6.4.4.1 策略：or 连接"类型"与"距离"两种判断 Strategy: "or" links a type check and a distance check

图5：流星雨——宝石永存、硬币速逝,用 or 合并"是宝石"与"够近"两条收集规则

这一关把 or 的用法推进了一层——两边连接的不再是同类判断，而是两种不同的问题。设定很巧妙：流星带来宝石和硬币，但硬币里的金属很快消失、宝石则永远留存。所以策略是：宝石无论远近都值得去捡，硬币只有在很近（省时省力）时才捡。

算法思路是先用 distanceTo 算出到物品的距离,再写 if item.type == "gem" or distance < 20——左边管宝石(靠类型),右边管近处硬币(靠距离)。只要满足任意一条就 moveXY 前往。这关让你真正体会到:or 能把"依据完全不同的两个条件"糅进同一个决策里,这是它比 != 更灵活的地方。

6.4.5 森林影子（Forest Shade）

6.4.5.1 策略：双 or 分别管敌人与物品 Strategy: two "or" blocks for enemies and items

图6：森林影子——藏身树林,用 or 只锁定投矛手/矮人,只收集宝石/硬币

这一关是"盐碱地"模式的巩固与综合。你藏身密林，大食人魔看不见你，正好从容行动。规则清晰：只攻击 "thrower"（投矛手）或 "munchkin"（矮人）；只收集 "gem"（宝石）或 "coin"（硬币）；其它一概不碰。

算法思路仍是主循环里两段并列的 or 判断:一段筛敌人 enemy.type == "thrower" or enemy.type == "munchkin" 后攻击,一段筛物品 item.type == "gem" or item.type == "coin" 后收集。结构与"盐碱地"高度对称,是对"用 or 建白名单"这一模式的熟练化训练。多写几遍,这套"找到→按 or 名单筛选→行动"的骨架就会成为你的肌肉记忆。

6.4.6 守护者（概念挑战 · Guardian）

6.4.6.1 策略：独立写出 or 筛敌逻辑 Strategy: write the "or" filter on your own

这是本单元的概念挑战，检验你能否脱离提示独立运用 or。任务纯粹：只攻击 type 是 "munchkin" 或 "thrower" 的敌人。没有分步注释，需要你自己回忆并搭出完整结构。

算法思路是最经典的"or 白名单"三步:主循环 findNearestEnemy 找到最近敌人 → if enemy.type == "munchkin" or enemy.type == "thrower" 判断它是否在打击名单里 → 是则 attack。关键要写出两个完整的 == 判断,而不是偷懒写成 == "munchkin" or "thrower"。

# 只攻击类型是"矮人"或"投掷者"的敌人
while True:
    enemy = hero.findNearestEnemy()
    if enemy.type == "munchkin" or enemy.type == "thrower":
        hero.attack(enemy)
概念挑战的意义:概念挑战刻意撤掉了脚手架式提示,考验你能否独立成篇。若你能顺手写出上面的结构,并且没有掉进"or 右边漏写 enemy.type =="的陷阱,说明 or 的语法和"白名单"思维都已经真正长进了你的脑子里。

6.5 常见错误

Common Mistakes

6.5.1 新手最容易踩的坑（Pitfalls for Beginners）

6.5.1.1 逻辑或运算符环节的典型问题 Typical issues with the "or" operator

图7：or 右边漏写判断、== 写成 =、布尔值小写,是本单元最常见的失误
易错点清单：
  • or 右边只写值不写判断——把 type == "gem" or "coin" 当成"等于宝石或硬币"是头号错误，右边必须写完整的 type == "coin"。
  • 把 == 误写成 =——赋值是一个等号，判断相等是两个等号，条件里写错会直接报错或逻辑出错。
  • 布尔值大小写写错——Python 里是 True/False(首字母大写)，写成 true/false 会报错。
  • 把布尔值 True 和字符串 "True" 混淆——一个是真假值，一个是文本，两者不相等。
  • 该用 or 时却抄了两段重复 if——动作相同的多种情况应合并成一个 or，否则难维护。
  • or 与 and 混淆——or 是"满足其一即可"，and 是"必须都满足"，用错会让筛选范围完全相反。
  • 忘记先确认对象存在——在某些关卡直接读 enemy.type 前若没确认敌人存在，周围没敌人时可能出错。
